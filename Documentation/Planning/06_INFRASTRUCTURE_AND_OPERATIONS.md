## 2. Initial topology, local paths, and credentials

### OPS-003 — Local deployment [PRD-001, PRD-014]

Initial scope: one OS account and one Alify user per installation, two existing local hosts supervised by a proposed launcher, one coordinated local SQLite database, bounded in-memory caches, OS credential adapters, and a local browser UI. No Redis, cloud database, broker, hosted account service, mandatory container, or microservice cluster. Offline standalone imports/rules/review work without Spotify, Gemini, Genius, scraping browsers, or Doppler. Network operations occur only after explicit opt-in to an authorized provider lane.

Launcher plan: validate writable per-user paths and credentials-store availability; acquire a single-installation lock; migrate under an exclusive DB lock; bind exact loopback listeners; establish protected browser sessions; open the system browser; display port/conflict/error recovery instructions. No `0.0.0.0`, LAN listener, remote reverse proxy, or fallback to a public port. Fixed versus configurable ports must be reconciled with registered OAuth redirect rules. Validate `Host` and origin; loopback is not sufficient authentication. A packaged HTTPS option needs a deliberate certificate/trust lifecycle; do not install broad machine trust or rely on development certificates silently. If HTTP loopback is selected, disclose limitations and test ARCH-014 compensating controls.

Proposed path conventions (resolve via platform APIs, not literal environment-variable strings):

| OS | Durable data/config | Logs and rebuildable cache |
| --- | --- | --- |
| Windows | `%LOCALAPPDATA%\Alify\Data\alify.db`, `%LOCALAPPDATA%\Alify\Config\`; backups under `Data\Backups\` | `%LOCALAPPDATA%\Alify\Logs\`, `%LOCALAPPDATA%\Alify\Cache\` |
| macOS | `~/Library/Application Support/Alify/Data/alify.db`, sibling `Config/` and `Data/Backups/` | `~/Library/Logs/Alify/`, `~/Library/Caches/Alify/` |
| Linux | `$XDG_DATA_HOME/alify/alify.db` (default `~/.local/share/alify/`); `$XDG_CONFIG_HOME/alify/` (default `~/.config/alify/`); backups under data directory | `$XDG_STATE_HOME/alify/logs/` (default `~/.local/state/alify/logs/`); `$XDG_CACHE_HOME/alify/` (default `~/.cache/alify/`) |

These are proposed destinations, not paths currently populated. Config contains non-secret preferences and opaque credential references only. Restrict Windows ACLs to the user/system as needed; Unix directories mode 0700 and private files 0600. Avoid roaming/synced folders by default; warn if the user relocates into sync. No DB/log/key writes to repository, install directory, shared temp, or browser storage. Separate multiple development profiles explicitly; release supports one active installation profile, not multi-tenancy. Validate supported OS/RIDs before claiming platform support; Windows is the current inspected machine, macOS/Linux plans remain gated by CI/packaging tests.

### OPS-004 — Credential integration and authentication [PRD-002, PRD-012]

Proposed `ICredentialStore` adapters: Windows Credential Manager protected for the current user; macOS Keychain; Linux Secret Service/libsecret where available. Package/native dependencies and permission prompts need proof-of-concept validation. Do not label these adapters implemented. If store is locked/unavailable, report a recoverable error or offer clearly disclosed session-only in-memory use; **never** fall back to plaintext JSON/SQLite/environment files. Development user secrets are a convenience, not a production encrypted store.

Store Gemini key and Spotify refresh token in the OS store. Keep access tokens short-lived in memory; persist rotated refresh token before retiring the prior reference. Background monitor obtains credentials from a local broker independent of `HttpContext`; refresh uses a single-flight lock, bounded cancellation, auth generation checks, and redacted failures. Public-client PKCE distributes only client ID and exact redirect configuration, not client secret. Scope defaults exclude playlist modifications; enabling controls requests needed modify-playback authorization explicitly. ARCH-015 defines verifier/state and replay rules.

Keys are never returned to UI, in URLs, logs, exceptions, metrics, SSE, diagnostic archives, or backups. UI offers set/replace/delete with masked status. Disconnect clears session, OS token, broker memory, background authorization, pending refresh, caches, and auth generation. An account switch cannot reuse an old cache/action. Revocation outside Alify is detected on definitive auth failure and stops monitoring until reconnection; clearing local credentials alone is not proof the provider grant was revoked. Give instructions for provider-side revocation where direct revocation is unavailable.

### OPS-005 — Provider/network behavior and bounded work [PRD-003, PRD-006, PRD-011, PRD-012]

- Outbound destinations are allowlisted per adapter and reviewed; redirects may not escape the permissioned destination list. No arbitrary URL import fetch, private Spotify endpoint, cookies/hooks, or scraper fallback. User-file/paste import is the default permissioned lane. Third-party lyric-provider use requires rights/terms validation, not just a reachable API.
- Proposed initial deadlines: local API operations five seconds; official read/refresh calls ten seconds; skip dispatch ten seconds; lyric provider 15 seconds; Gemini 30 seconds; complete cancellable job 60 seconds. Deadlines include queue wait/retry time, not just socket time. Imports are capped at DATA limits. UI may poll jobs instead of holding long requests.
- Link request cancellation, job cancellation, source-deletion generation, auth revocation, and host shutdown. Use cancellable lock acquisition, bounded channels, and disposable HTTP/DB resources. Do not `Task.Run` every CPU operation; bounded local CPU work runs with measured concurrency and cooperative checks. Initial local analysis concurrency two, provider analysis concurrency one, playback dispatch one.
- Authorized idempotent reads may get at most one retry within the total deadline, with jitter and `Retry-After` honored; if cooldown exceeds deadline, return unavailable and schedule only a fresh explicit/monitor read later. Suspend/rate-limit the monitor, never spin on 429. OAuth code exchange/refresh ambiguity needs reauth/broker reconciliation, not uncontrolled token retries.
- **No automatic skip retry**, including SDK/HTTP retry handlers. Timeout after possible dispatch is `OutcomeUnknown`; bounded subsequent observations do not resend. No retry/fallback of a chargeable uncertain Gemini request; preserve budget reservation. No automatic fallback to OpenRouter/Mistral or changing the consented model.
- Consent and transactional budget reservation precede any Gemini transfer. Configure provider-side caps if available and disclose estimate/billing uncertainty. Logs report usage counters, not text. Standalone local rules remain available without a key; beyond their language/interpretive scope they explicitly abstain.
- Stop/disconnect/deletion blocks new dispatch immediately, requests cancellation, and reports already submitted external work honestly. Shutdown drains local writers for at most five seconds and terminates hosts within ten seconds proposed; journal unresolved dispatched actions as unknown, never replay at restart.

## 3. SQLite, backups, migration, and rollback

### OPS-006 — Local persistence safety [PRD-001, PRD-008, PRD-012, PRD-013]

SQLite is proposed, not currently in package references. Use foreign keys, parameterized SQL, short transactions, explicit schema version/checksum history, a single logical writer coordinator across hosts, and bounded lock wait (proposed two seconds). Evaluate WAL for UI read responsiveness; do not enable it without coordinating backup/checkpoint/deletion and testing disk behavior. Durability settings must protect action dispatch intent and budget reservation; do not relax synchronous durability merely for benchmarks.

At startup, inspect disk space and supported schema before exposing mutations. Proposed low-space threshold: less than 100 MiB free or less than twice the estimated migration/backup space, whichever is greater, disables imports/migrations and displays recovery guidance. If action-intent journaling fails, **do not send playback commands**. DB corruption/unwritable storage enters read-only/degraded mode where safely possible, never silently creates a replacement DB or converts unavailable data to `Allow`.

**Backup plan:** use SQLite online backup API or a verified quiesced consistent snapshot, never copy only a live main DB while ignoring WAL. Keep at most three local snapshots/30 days by default, each with schema/app version, timestamp, checksum, and integrity result. Encrypt/protect to the same local threat standard and permissions as the source; credentials are excluded. Permission restrictions may prohibit source retention in backups; honor them. Back up before every migration and prior to installation upgrade when data exists. No off-device backup/upload by default. User export warns about lyric permissions and privacy.

**Migration plan:** launcher takes installation/migration locks and stops other writers; verifies current schema/version and space; produces and integrity-checks backup; applies numbered/checksummed transactional additive migration; runs foreign-key/integrity/domain checks; records migration completion; releases services. A failed migration rolls back its transaction and leaves the old DB untouched. Do not start a binary against a newer unsupported schema. Destructive migrations require separately approved data retention/export and downgrade plan; no automatic dropping/rewriting immutable evidence.

**Rollback plan:** prefer disabling a feature or reverting binary only when old binary supports current schema. Otherwise stop both hosts, preserve the failing DB privately, restore a verified pre-upgrade backup, apply deletion-ledger reconciliation, and launch the matching prior binary. Record that new data since backup may be lost; get user confirmation rather than hiding it. Never restore provider credentials from backup, auto-resume monitors, replay unresolved actions, or send pending provider requests. Deletion reconciliation prevents old backups resurrecting erased sources. Verify restore with integrity and representative source/evidence queries before declaring recovery.

Ordinary file/SQLite deletion is not guaranteed physical erasure; WAL, backups, SSD wear leveling, filesystem/OS snapshots and exported copies matter. Recommend OS full-disk encryption; stronger encryption/key destruction would be a separate reviewed implementation choice.

## 4. Privacy-preserving diagnostics and proposed SLOs

### OPS-007 — Diagnostics [PRD-008, PRD-011, PRD-012]

Local structured logs default to warning/error plus bounded lifecycle summaries. Redaction/allowlisting occurs before serialization: no credentials/cookies/OAuth codes/state/verifier, auth headers, query strings, user names/account IDs, track titles/artist names, lyrics/evidence, provider request/response bodies, file contents, or full import paths. Hashes can be correlatable content identifiers; do not log content hashes or raw recording IDs by default. Use random local job/action correlation IDs and route templates, not raw URL/path. Avoid logging exception text wholesale when SDK errors embed response bodies; map to safe codes. Current HTTP/console logging is not claimed to meet this policy.

Proposed logs rotate at 5 MiB each, five files maximum, seven-day age cap. Count aggregate durations/status codes/cache hits/queue depth/cancellations/budget usage without content dimensions. Diagnostics UI shows local-only metrics, versions, supported capabilities, last safe error code, and blocked-feature state. No telemetry upload default. User diagnostic export previews fields and supports excluding all database/files; include safe versions and event summaries only by default. Disable crash dumps containing process memory by default or gate collection on explicit informed consent and local access controls. Delete diagnostic archives through the same privacy UI; uploaded user archives cannot be recalled automatically.

## 5. Release packaging and CI plan

### OPS-008 — Planned release pipeline [PRD-002, PRD-005, PRD-008, PRD-012, PRD-014]

The existing Playwright workflow is not this pipeline. Implementation PRs should add a bounded .NET pipeline and app-specific offline tests rather than claim they already exist.

1. Establish stable SDK reconciliation (OPS-002), declared package sources and reproducible restore policy; secret scan includes launch settings and generated artifacts. Rotate any exposed credentials before distribution. Review dependency license/security advisories and produce a version inventory/SBOM.
2. Restore, build, and test Core/Lyrics/Spotify in Release using the approved SDK. Proposed commands include `dotnet restore Alify.sln`, `dotnet build Alify.sln --configuration Release --no-restore`, and `dotnet test Alify.sln --configuration Release --no-build` **after adding real test projects to the solution**. A currently testless solution is not a successful acceptance suite. Do not introduce build commands into this documentation task.
3. Unit/contract tests: all DATA-T fixtures, deterministic policy, provider-neutral boundaries, permissions, budget concurrency, action uncertainty. Integration tests: temporary SQLite, migrations/restore/deletion, fake official API and fake Gemini, OS credential-adapter failure modes, cancellation. Tests deny outbound internet by default and never need live keys or real playback.
4. App-specific Playwright tests launch supervised test hosts with fixture adapters, explicit timeouts, local-only browser navigation, and no external CDN dependence. Replace reliance on sample playwright.dev tests as release evidence. Validate keyboard flow, focus/error summaries, contrast, accessible line/evidence navigation, status announcements, and readable unknown-action warnings; combine automated checks with recorded manual screen-reader review.
5. Security fixtures: PKCE/state replay, Host/origin/CSRF rejection, unauthorized SSE, output-cache isolation, secret redaction, injection text, permissions expiry, redirect escape prevention, disconnect background invalidation, and blocked semantic Spotify bridge. Never exercise private endpoints/cookies/hooks.
6. Packaging choice: proposed Windows x64 first, self-contained .NET 10 packages for existing web hosts and launcher; evaluate arm64/macOS/Linux only after RID-specific packaging, credential, browser, and accessibility tests. Self-contained simplifies end-user runtime setup but increases size and requires redistributing runtime security patches; compare measured package size/updates with framework-dependent alternative. Do not assume trimming/single-file compatibility; test before enabling. No mandatory Playwright scraping browser or Node runtime in production package.
7. Include static assets/offline help, explicit version/schema compatibility metadata, licenses/SBOM, checksums, install/uninstall and migration/deletion instructions. Exclude launch settings, secrets, development certificates, local DB/logs, and tests' sensitive artifacts. Signing/notarization requires assigned ownership/credentials and platform review; no signed/notarized claim until verified.
8. Smoke-test clean install, first launch without network, opt-in fake provider workflows, port conflict, locked store, upgrade/rollback, and uninstall preserving versus explicitly deleting data. User-controlled updates verify authenticity/checksum and back up before migration; no forced update during dispatch. Release only after acceptance/SLO evidence and security/policy blockers are reviewed. Keep semantic bridge absent/blocked.

Network-required CI restore/browser downloads belong to future controlled CI, not initial runtime dependencies. Set job/task deadlines and avoid long-lived watchers; external integration tests, if ever needed, require an explicit isolated test account, authorization, and manual gate, and cannot issue uncontrolled skip commands.

## 7. Conditional future hosted infrastructure gates

**OPS-009 — Not initial scope:** Hosted deployment, accounts/multi-user auth, cloud storage, distributed cache/Redis, queues, hosted model credentials, and microservices require a new product scope and threat model. Do not provision them or make monthly dollar promises in this pack.

A future hosting proposal needs measurable demand (concurrency/data retention/provider traffic), written rights and Spotify policy review for each data flow, a security/privacy assessment, jurisdiction and consent/retention plan, tenant isolation, credential/KMS design, backups/restore/disaster recovery tests, regional availability objectives, accessible support procedures, incident ownership, and a cost model based on measured requests/tokens/storage/egress/licensing/support. Set budget alarms and capacity limits before approval; compare a modular monolith first. Distributed components require measured bottlenecks, not speculative scale. Hosting does not unlock the semantic Spotify bridge or waive source/provider permission gates.
